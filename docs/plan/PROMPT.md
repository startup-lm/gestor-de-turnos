# Prompt Original del Plan Multi-Cliente

```markdown
MODO TESTING (regla que prevalece sobre todo lo demás): este trabajo es una mejora interna mía y por ahora no puede afectar de ninguna forma a mis dos clientes en producción, que usan el sistema hoy. Las carpetas hooligans y hellfish son de SOLO LECTURA para vos: no modifiques, no commitees, no cambies ramas ni configuración en ellas. Todo lo que construyas vive en gestor-de-turnos, en ramas nuevas. Todo lo que se pruebe se prueba en el Vercel y el Supabase actuales de gestor-de-turnos (que uso solo yo para testing) y, para validar el schema de un cliente, en un proyecto de Supabase de testing adicional con solo estructura. Ninguno de estos entornos apunta nunca a los proyectos reales de los clientes. Nada se migra a producción hasta que yo lo diga explícitamente en la Fase 6. Si alguna acción tuya o mía pudiera tocar producción de un cliente, frená y avisame antes.

Contexto: tengo tres carpetas en este workspace: gestor-de-turnos (proyecto base, donde desarrollo mejoras y testeo), barberia-hooligans y hellfish-barber-studio (dos clientes, barberías). Hooligans y hellfish nacieron como copias del base, tienen historiales de git independientes, y cada uno tiene su propio repo de GitHub, su propio Vercel y su propio proyecto de Supabase. Los cambios de schema los hice siempre corriendo queries a mano en el dashboard de Supabase, sin migraciones versionadas. Casi todas las diferencias entre repos son de UX/UI, y hay pocas features distintas. Stack: Next.js, Supabase, Vercel.

Objetivo final: que gestor-de-turnos sea el único repo con código y que cada cliente sea solo un deploy (su propio Vercel y su propio Supabase) apuntando a ese mismo código, con diferencias resueltas por configuración en base de datos y feature flags. Quiero poder llevar mejoras del base a todos los clientes de forma simple y activarlas por cliente solo cuando lo acepten. Voy a sumar más clientes, así que tiene que escalar.

Cómo quiero que trabajes: andá fase por fase y al terminar cada una resumí lo hecho y esperá mi aprobación antes de seguir. Antes de cada acción importante explicame en prosa qué vas a hacer y por qué, y cuando uses un concepto de migraciones de Supabase (migración inicial, delta, migration repair, retrocompatibilidad, etc.) explicalo con un ejemplo concreto de este proyecto. Soy ingeniero y conozco SQL y Next.js, pero soy nuevo en migraciones versionadas, así que no me expliques lo básico de programación. Si te falta información o hay ambigüedad, preguntame en lugar de asumir.

Continuidad entre chats: este plan se ejecuta en varios chats, uno por fase. Antes de la Fase 0, creá en gestor-de-turnos la rama plan/multi-cliente y guardá este mismo prompt completo en docs/plan/PROMPT.md. Al cerrar cada fase, escribí docs/plan/fase-N.md con lo hecho, las decisiones tomadas y por qué, los hallazgos y lo pendiente, y actualizá docs/plan/ESTADO.md con la fase actual, qué fases están aprobadas y las preguntas abiertas. Al empezar un chat nuevo vas a leer PROMPT.md y ESTADO.md primero. No guardes en estos archivos ningún secreto ni datos reales de clientes finales.

Todo lo que necesites de mi parte pedímelo explícitamente, con los pasos exactos para obtenerlo: qué comando correr o qué botón tocar en el dashboard, en qué carpeta o proyecto, qué resultado esperar y cómo pasártelo (por ejemplo, un dump de schema, un backup, una variable de entorno, un dato de configuración de Vercel). No intentes obtenerlo por tu cuenta ni lo inventes. Si algo lo puede obtener solo yo, decímelo y esperá.

Reglas duras: no ejecutes nada contra ninguna base de datos de Supabase (ni lectura ni escritura); trabajá solo con archivos locales y con los dumps de schema que yo te pase. No hagas push, force push, ni borres ramas o repos. No imprimas ni copies secretos de los .env. Todo cambio de código va en una rama nueva de gestor-de-turnos, nunca directo en main. Los datos reales de clientes finales de las barberías no deben copiarse a entornos de prueba; para probar usamos solo estructura o datos de prueba.

Fase 0, reconocimiento (solo lectura): revisá el stack, la estructura de carpetas, el estado de git de las tres carpetas y cómo se lee hoy la configuración del local (colores, fotos, barberos, redes) en el base. Contame qué encontraste.

Fase 1, diferencias de código (solo lectura): compará el estado actual de los archivos de hooligans y hellfish contra el base (no los historiales). Armá un informe que clasifique cada diferencia en tres grupos: valores que deberían pasar a configuración del cliente, mejoras que deberían entrar al base para todos, y funcionalidad realmente específica de un cliente que debería ir en el base detrás de un flag. Proponé cuál de los dos clientes es mejor piloto según cuánto diverge. Frená acá.

Fase 2, schema: pedime los dumps de schema (solo estructura, sin datos) de los tres Supabase y explicame cómo sacarlos. Compará los tres, señalá columnas o tablas que existan en un cliente y no en el base y proponé el estado de schema que debería quedar como verdad. Frená acá.

Fase 3, flags y configuración en el base: antes de empezar, pedime que saque un backup del Supabase del base y esperá mi confirmación. Después, en una rama nueva de gestor-de-turnos, agregá un campo jsonb de features a la tabla de configuración y un helper tipo isEnabled('nombre') que lea el valor del cliente y caiga a un default definido en código. Toda feature nueva sale con el default apagado. Mové al sistema de configuración lo que clasificamos como valores y poné detrás de flags las variantes de pantalla, de modo que la configuración de cada cliente reproduzca exactamente lo que tiene hoy. Explicame cada decisión de diseño.

Fase 4, migraciones: inicializá Supabase CLI en el base, versioná el schema verdad como migración inicial y escribí para cada cliente una migración delta que lo lleve a ese estado, sin ejecutarla. Prepará los comandos de migration repair y un script o workflow de GitHub Actions que aplique migraciones pendientes a la lista de proyectos, y documentá la regla de que toda migración debe ser retrocompatible (agregar, no borrar ni renombrar en el mismo paso). Pedime que cree un proyecto de Supabase de testing con el schema del piloto (sin datos reales) y darte los pasos para hacerlo; yo ejecuto los comandos ahí y te cuento el resultado.

Fase 5, entorno de pruebas completo: proponé la estrategia de ramas (main para pruebas, release para los clientes) y dame los pasos exactos para conectar el Vercel existente del base con las variables de entorno que apunten solo a los Supabase de testing. Pedime que valide que la app de testing se comporta igual que el cliente piloto en producción, con una lista de chequeos concreta (pantallas, flujos de reserva, colores, fotos, barberos, redes).

Fase 6, migración a producción (NO empezar sin mi orden explícita): cuando yo haya probado todo y diga "go", armá el plan de cutover para el piloto, con backup previo, orden de pasos, tiempo de ventana estimado, plan de rollback y los comandos exactos para que yo los ejecute. Después repetimos para el segundo cliente.

Empezá por crear la rama y guardar este prompt, y luego seguí con la Fase 0.
```
